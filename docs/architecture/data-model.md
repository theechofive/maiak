# Data model

Postgres 15 (RDS), database `maiak`. Migrations are SQL files (goose) in `backend/migrations`, applied by the `migrate` Job as `maiak_owner`; the current list and the lint rules are in the [migrations runbook](../runbooks/migrations.md). This page describes the schema as the migrations up to 2026-10-21 (plans, P-01) leave it (checked against a migrated database).

## Decisions that are expensive to change later

1. **IDs:** `uuid` v7 generated by the application (Postgres 15 has no native `uuidv7()`). `check_results` and `result_rollups_hourly` have composite keys instead of a row id.
2. **`tenant_id` on every tenant-scoped table, including results.** References between tenant tables use composite `(tenant_id, id)` foreign keys, so a row cannot point at another tenant's row even through a bug.
3. **RLS enabled and forced** on every table with `tenant_id`: policy `tenant_isolation` (all commands) `USING/WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)`. The app sets `app.tenant_id` with `SET LOCAL` inside `db.WithTenantTx`. `tenants`, `users`, `auth_identities`, `probe_locations` and `plans` are global and have no RLS.
4. **Roles:** `maiak_owner` owns every object and runs migrations; `maiak_api` (api) and `maiak_worker` (worker and jobs) are runtime roles, never owners, never `BYPASSRLS`. Work that must span tenants (claims, partitions, rollups, retention, outbox, session lookup and purge) goes through `SECURITY DEFINER` functions owned by `maiak_owner` (below). Roles and the database are created by `maiakctl db bootstrap` (hook Job, ADR-0014), not by migrations.
5. **`check_results` is partitioned by month** on `checked_at`; retention detaches and drops whole expired monthly partitions after checking that their rollups are complete (ADR-0016, ADR-0021, ADR-0060). Raw data is kept at least 30 days (up to about 61).
6. **Check type and parameters are separate:** `monitors.type` (`http` only, CHECK) + `config jsonb` (`url`, `expectedStatus`). TCP, DNS and Kubernetes checks need no schema change.
7. **Locations:** `probe_locations` + `monitor_locations`. Schedule, lease and counters are kept **per (monitor, location)** in `monitor_location_state`; the aggregated status lives in `monitor_state` (quorum rule in `internal/incidents/machine`: down when every selected location is down).
8. **Transactional outbox:** `notification_deliveries` rows are written in the same transaction as the incident transition (only when the tenant has an active Slack channel, ADR-0019). `jobs` delivers them with retries and a per-channel rate limit (ADR-0051).
9. **Secrets in the DB are encrypted** (AES-256-GCM with a `key_id` prefix for rotation): the Slack webhook URL in `notification_channels.config_encrypted`.
10. **Audit log** from day one (`audit_log`, insert-only for runtime roles; metadata never contains URLs or secrets).
11. **Users exist from the start:** `users`, `memberships`, `auth_identities` (unused until OAuth). The single admin from the Secret is upserted at api start and bound to the tenant `default` as `owner`.
12. **Plans and quotas (ADR-0093):** every tenant has a plan (`tenants.plan_key` → `plans.key`, default `free`). Effective limits are the plan's `limits` overridden key by key by `tenants.limits`; `internal/plans` resolves them and checks them under the tenant row lock in the transaction that creates the row.
13. **Time and enums:** `timestamptz` (UTC); enums as `text` + `CHECK`; soft delete for monitors and tenants (`deleted_at`).

## Partitions
Partitions are named `check_results_pYYYYMM` (UTC month) and created by `ensure_partitions()` for the current and the next two months, each with `ENABLE`/`FORCE ROW LEVEL SECURITY`, its own `tenant_isolation` policy and the parent's grants (api `S`, worker `S I`). The results migration calls it once; afterwards the worker calls it at start and hourly and `jobs` daily, so inserts never depend on one process. There is no default partition: a result whose month has no partition fails to insert (L-040).

## Retention
`jobs` runs the retention task (housekeeping name `drop_expired_partitions`, kept for metric continuity) daily under an advisory lock, each step in its own short transaction (ADR-0060):
1. `list_droppable_partitions()` returns partitions whose month ended more than 30 days ago (never the current month), attached or left detached by an interrupted run;
2. `detach_expired_partition(name)` re-validates the name, ownership and age, requires complete rollups (every `(monitor, location, hour)` with raw rows has a rollup with the same total), then a plain `DETACH` under `lock_timeout = '1s'` (not `CONCURRENTLY`, L-091); it returns false and keeps the partition when rollups are incomplete;
3. `drop_detached_partition(name)` drops only a detached, expired plain table owned by `maiak_owner` that matches the name pattern.

Hourly rollups are designed to be kept 13 months, but nothing deletes them yet (L-110).

## SECURITY DEFINER functions
All are owned by `maiak_owner`, pin `search_path = public, pg_temp`, are not executable by PUBLIC and are allow-listed in the schema lint (`definerAllowList` in `backend/migrations/integration_test.go`) with the only role that may execute them. They read and write through `owner_*` policies that apply to `maiak_owner` only.

| Function | Grantee | Called by | Purpose |
|---|---|---|---|
| `auth_lookup_session(token_hash)` | `maiak_api` | api (`auth.Service.Authenticate`) | Finds a session before the tenant is known |
| `auth_login_tenant(user_id)` | `maiak_api` | api (`auth.Service.Login`) | The tenant a login binds to: the user's oldest membership in a tenant that is not deleted, or NULL (P-02) |
| `reset_monitor_runtime(monitor_id)` | `maiak_api` | api (`monitors` pause, resume, URL change, through `scheduler`) | Resets the monitor's location rows (status unknown, lease dropped, next run within 30 s); tenant taken from `app.tenant_id` |
| `claim_due_monitors(n, p_location)` | `maiak_worker` | worker (`scheduler.Claim`), every second | Leases up to `n` due rows of one location, skipping paused or deleted monitors and suspended or deleted tenants |
| `ensure_partitions()` | `maiak_worker` | worker (start, hourly), jobs (daily) | Creates missing partitions |
| `compute_rollups(from_hour, to_hour)` | `maiak_worker` | `compute_rollups_catch_up`; the previous jobs release; manual backfills | Upserts hourly rollups of a range under an advisory xact lock |
| `compute_rollups_catch_up(max_hours, lookback_hours)` | `maiak_worker` | jobs, every 5 minutes (48, 3) | Rolls up from the `rollup_state` watermark (at most `max_hours`, never older than 7 days) plus the lookback, then moves the watermark (ADR-0090) |
| `list_droppable_partitions()` | `maiak_worker` | jobs, daily | Retention step 1 |
| `detach_expired_partition(name)` | `maiak_worker` | jobs, daily | Retention step 2 |
| `drop_detached_partition(name)` | `maiak_worker` | jobs, daily | Retention step 3 |
| `purge_expired_sessions()` | `maiak_worker` | jobs, hourly | Deletes expired sessions |
| `claim_deliveries(n)` | `maiak_worker` | jobs, every second | Leases ready outbox rows (oldest first per monitor), sets `claim_token`, requeues expired claims and counts the attempt |
| `finish_delivery(id, token, status, error, retry_at)` | `maiak_worker` | jobs | Records an outcome only for the holder of the claim token |

## Added later by additive migrations
`status_pages`, `status_page_components`, `incident_updates`, `api_keys`, plans and billing, more channel types, agent registrations and tokens.

## Retention and sizing (design target)
Raw results 30 days (configurable per tenant or plan later), hourly rollups 13 months (deletion not implemented, L-110). Rough size at 100 000 monitors and one location: 144 M rows per day, about 4.3 B rows over 30 days (0.6-0.8 TB with indexes). Several locations multiply this. See [ADR-0012](../adr/0012-scale-path.md); the load test is L-010.
