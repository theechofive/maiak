# Data model

Postgres 15 (RDS), database `maiak`. Migrations are SQL files (goose) in `backend/migrations`, applied by the `migrate` Job as `maiak_owner`.

## Decisions that are expensive to change later (fixed now)

1. **IDs:** `uuid` v7 generated by the application (Postgres 15 has no native `uuidv7()`). Time-ordered, no collisions across environments, do not reveal counts. High-volume `check_results` uses a composite key instead of a row UUID.
2. **`tenant_id` on every tenant-scoped table, including results.** References use composite `(tenant_id, id)` foreign keys, so a row cannot point at another tenant's row even through a bug.
3. **RLS forced** on tenant tables: `USING/WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid)`. The app sets it with `SET LOCAL` inside `db.WithTenantTx`.
4. **Roles:** `maiak_owner` (owns objects, migrations), `maiak_api` (runtime, RLS applies), `maiak_worker` (runtime for worker and jobs, RLS applies, no `BYPASSRLS`). The worker claims work through `SECURITY DEFINER` functions such as `claim_due_monitors(n)` and writes results under `SET LOCAL app.tenant_id`. Roles and the database are created by `maiakctl db bootstrap` (hook Job, ADR-0014), not by migrations.
5. **`check_results` is partitioned by month** on `checked_at`. Retention is `DROP PARTITION` of monthly partitions, so raw data is kept at least 30 days (up to about 61); rollups are computed first (ADR-0016). `jobs` creates partitions ahead of time.
6. **Check type and parameters are separate:** `monitors.type` (`http` now) + `config jsonb`. TCP, DNS and Kubernetes checks need no schema change.
7. **Locations:** `probe_locations` + `monitor_locations`. State and schedule are kept **per (monitor, location)** in `monitor_location_state`; the aggregated monitor status lives in `monitor_state` and is computed by a quorum rule (default: down when all selected locations are down).
8. **Transactional outbox:** `notification_deliveries` rows are written in the same transaction as the incident transition. `jobs` delivers them with retries and per-destination rate limits.
9. **Secrets in the DB are encrypted** (AES-256-GCM, `key_id` prefix for rotation): Slack webhook URLs now, request headers with tokens later.
10. **Audit log** from day one (`audit_log`, insert-only for runtime roles).
11. **Users exist from the start:** `users`, `memberships(tenant, user, role)`, `auth_identities` (for future OAuth). The single admin from the Secret is upserted into `users` at startup and bound to the default tenant as `owner`.
12. **Time and enums:** `timestamptz` (UTC); enums as `text` + `CHECK`; soft delete for monitors.

## MVP tables

| Table | Notes |
|---|---|
| `tenants` | slug (future subdomain), status, `limits jsonb` (max monitors, min interval), soft delete |
| `users` | global (not tenant-scoped), `email citext` unique, `password_hash` nullable |
| `memberships` | PK (tenant_id, user_id), role in owner/admin/member/viewer |
| `auth_identities` | (provider, subject) unique; unused until OAuth |
| `sessions` | server-side sessions; only the SHA-256 of the token is stored; `csrf_token`; lookup by token hash through a `SECURITY DEFINER` function because the tenant is not known yet |
| `audit_log` | who, what, when; insert-only |
| `monitors` | name, type, `config jsonb`, interval, timeout, `paused`, failure threshold, quorum rule, soft delete |
| `probe_locations` | code, region/country/city, provider/network, kind (platform or agent), status |
| `monitor_locations` | which locations run which monitor |
| `monitor_location_state` | per (monitor, location): status, consecutive failures, `next_run_at`, lease; hot, high update rate, tuned for HOT updates and autovacuum |
| `monitor_state` | aggregated status, `status_changed_at`, `last_error_kind`, `last_checked_at`, `tls_warned_not_after`, current incident |
| `check_results` | partitioned; tenant, monitor, location, `checked_at`, status, http status, latency, error kind (truncated message), TLS expiry |
| `result_rollups_hourly` | per (monitor, location, hour): totals, ok count, latency stats; kept 13 months |
| `incidents`, `incident_monitors` | automatic incidents now; many-to-many prepared for manual incidents spanning monitors (status page) |
| `notification_channels` | type (`slack_webhook` now), encrypted config |
| `monitor_channels` | which channels notify for which monitor |
| `notification_deliveries` | outbox: kind (opened/resolved/tls_expiring), status, attempts, last error |

## Added later by additive migrations

`status_pages`, `status_page_components`, `incident_updates`, `api_keys`, plans and billing, more channel types, agent registrations and tokens.

## Slice plan for migrations

Slice 1: `tenants`, `users`, `memberships`, `auth_identities`, `sessions`, `audit_log`, roles/grants/RLS scaffolding. Later slices add the rest in the order the features arrive.

## Retention and sizing (design target)

Raw results 30 days (configurable per tenant or plan), hourly rollups 13 months. Rough size at 100 000 monitors and one location: 144 M rows per day, about 4.3 B rows over 30 days (0.6-0.8 TB with indexes). Several locations multiply this. See [ADR-0012](../adr/0012-scale-path.md).
