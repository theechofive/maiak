# Data model

Postgres 15 (RDS), database `maiak`. Migrations are SQL files (goose) in `backend/migrations`, applied by the `migrate` Job as `maiak_owner`; the current list and the lint rules are in the [migrations runbook](../runbooks/migrations.md). This page describes the schema as the migrations up to 2026-11-06 (status page, P-05) leave it (checked against a migrated database).

## Decisions that are expensive to change later

1. **IDs:** `uuid` v7 generated by the application (Postgres 15 has no native `uuidv7()`). `check_results` and `result_rollups_hourly` have composite keys instead of a row id.
2. **`tenant_id` on every tenant-scoped table, including results.** References between tenant tables use composite `(tenant_id, id)` foreign keys, so a row cannot point at another tenant's row even through a bug.
3. **RLS enabled and forced** on every table with `tenant_id`: policy `tenant_isolation` (all commands) `USING/WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)`. The app sets `app.tenant_id` with `SET LOCAL` inside `db.WithTenantTx`. `tenants`, `users`, `auth_identities`, `probe_locations` and `plans` are global and have no RLS.
4. **Roles:** `maiak_owner` owns every object and runs migrations; `maiak_api` (api), `maiak_worker` (worker and jobs) and `maiak_statuspage` (the public status page renderer: read-only transactions, no table privileges, only `EXECUTE` on `status_page_snapshot`) are runtime roles, never owners, never `BYPASSRLS`. Work that must span tenants (claims, partitions, rollups, retention, outbox, session lookup and purge) goes through `SECURITY DEFINER` functions owned by `maiak_owner` (below). Roles and the database are created by `maiakctl db bootstrap` (hook Job, ADR-0014), not by migrations.
5. **`check_results` is partitioned by month** on `checked_at`; retention detaches and drops whole expired monthly partitions after checking that their rollups are complete (ADR-0016, ADR-0021, ADR-0060). Raw data is kept at least 30 days (up to about 61).
6. **Check type and parameters are separate:** `monitors.type` (`http` or `heartbeat`, CHECK) + `config jsonb` (`url`, `expectedStatus` for http; `graceSeconds` for heartbeats). TCP, DNS and Kubernetes checks need no schema change.
7. **Locations:** `probe_locations` + `monitor_locations`. Schedule, lease and counters are kept **per (monitor, location)** in `monitor_location_state`; the aggregated status lives in `monitor_state` (quorum rule in `internal/incidents/machine`: down when every selected location is down).
8. **Transactional outbox:** `notification_deliveries` rows are written in the same transaction as the incident transition, one per eligible channel whose events match (the monitor's selected channels that are organization-wide or of its project, or the active channels of its project when it selected none, ADR-0100, T-02). `jobs` delivers them with retries and a per-channel rate limit (ADR-0051) and queues reminders for incidents that stay open.
9. **Secrets in the DB are encrypted** (AES-256-GCM with a `key_id` prefix for rotation): the Slack webhook URL in `notification_channels.config_encrypted` (wiped when the channel is deleted).
10. **Audit log** from day one (`audit_log`, insert-only for runtime roles; metadata never contains URLs or secrets).
11. **Users exist from the start:** `users`, `memberships`, `auth_identities` (unused until OAuth). The single admin from the Secret is upserted at api start, bound to the tenant `default` as `owner` and is the only platform admin (`users.is_platform_admin`, ADR-0097); cross-tenant admin work goes through definer functions that check that flag, never through a role that bypasses RLS.
12. **Plans and quotas (ADR-0093):** every tenant has a plan (`tenants.plan_key` → `plans.key`, default `free`). Effective limits are the plan's `limits` overridden key by key by `tenants.limits`; `internal/plans` resolves them and checks them under the tenant row lock in the transaction that creates the row.
13. **Time and enums:** `timestamptz` (UTC); enums as `text` + `CHECK`; soft delete for monitors, tenants and notification channels (`deleted_at`).

## Partitions
Partitions are named `check_results_pYYYYMM` (UTC month) and created by `ensure_partitions()` for the current and the next two months, each with `ENABLE`/`FORCE ROW LEVEL SECURITY`, its own `tenant_isolation` policy and the parent's grants (api `S`, worker `S I`). The results migration calls it once; afterwards the worker calls it at start and hourly and `jobs` daily, so inserts never depend on one process. There is no default partition: a result whose month has no partition fails to insert (L-040).

## Triggers (T-02)
Two trigger functions, invoker rights, no runtime-role grants (a trigger needs none): `tenants_create_default_project` (`AFTER INSERT ON tenants`, inserts the Default project with `app.tenant_id` set to the new tenant for that insert and restored afterwards) and `monitors_fill_project` (`BEFORE INSERT ON monitors` when `project_id` is NULL, the tenant's Default project; dropped by the contract step L-285). `projects_uuidv7()` builds their ids (executable by `maiak_api`, which may insert tenants directly, L-210).

## Retention
`jobs` runs the retention task (housekeeping name `drop_expired_partitions`, kept for metric continuity) daily under an advisory lock, each step in its own short transaction (ADR-0060):
1. `list_droppable_partitions()` returns partitions whose month ended more than 30 days ago (never the current month), attached or left detached by an interrupted run;
2. `detach_expired_partition(name)` re-validates the name, ownership and age, requires complete rollups (every `(monitor, location, hour)` with raw rows has a rollup with the same total), then a plain `DETACH` under `lock_timeout = '1s'` (not `CONCURRENTLY`, L-091); it returns false and keeps the partition when rollups are incomplete;
3. `drop_detached_partition(name)` drops only a detached, expired plain table owned by `maiak_owner` that matches the name pattern.

Hourly rollups are designed to be kept 13 months, but nothing deletes them yet (L-110).

## SECURITY DEFINER functions
All are owned by `maiak_owner`, pin `search_path = public, pg_temp`, are not executable by PUBLIC and are allow-listed in the schema lint (`definerAllowList` in `backend/migrations/integration_test.go`) with the only role that may execute them. They read and write through `owner_*` policies that apply to `maiak_owner` only. The `admin_*` functions take the acting user as their first argument and refuse (SQLSTATE `MKA01`) unless it is an active platform admin; they share two internal invoker helpers that no runtime role may execute, `admin_require_platform_admin(actor)` and `admin_audit(...)` (inserts the audit row under the target tenant's `app.tenant_id` and restores the caller's).

## Retention and sizing (design target)
Raw results 30 days (configurable per tenant or plan later), hourly rollups 13 months (deletion not implemented, L-110). Rough size at 100 000 monitors and one location: 144 M rows per day, about 4.3 B rows over 30 days (0.6-0.8 TB with indexes). Several locations multiply this. See [ADR-0012](../adr/0012-scale-path.md); the load test is L-010.
