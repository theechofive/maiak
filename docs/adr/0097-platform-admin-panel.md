# ADR-0097: Platform admin panel: a flag, definer functions that check it, guard rails

- Status: Accepted
- Date: 2026-10-21

## Context
ADR-0092 decided a minimal platform admin panel (task P-04): list tenants with plan and usage, change a plan, suspend, soft-delete, list users and reset a password, every action audited, no impersonation, and cross-tenant access only through `SECURITY DEFINER` functions that check a flag inside, never through a role that bypasses RLS. Password recovery of registered users is done by the platform admin until email exists (L-170). This ADR records how it is built and why.

## Decision
- **The flag.** `users.is_platform_admin boolean NOT NULL DEFAULT false`. Only `auth_sync_platform_admin(user_id)` changes it, and only `BootstrapAdmin` calls it, for the user configured by `MAIAK_ADMIN_LOGIN`, at every start: the flag is set for that user and cleared for everyone else (a retired previous admin loses it with its owner role). The function refuses a user that is not an active owner of `default` or that has any other membership (the same rule as ADR-0095), so even a compromised api cannot hand the flag to a registered user without also making it the owner of `default`. `maiak_api` loses table-wide `INSERT` on `users` (it keeps `INSERT (id, email, password_hash, display_name)`, all that registration and the bootstrap write) and its column `UPDATE` grant never included the flag. No API grants or revokes it; there is one platform admin, the system admin. `GET /auth/me`, login and registration answer `isPlatformAdmin` in the user object (additive, camelCase like every field after ADR-0017; optional in the contract because an api of the previous release does not send it).
- **The guard.** Every operation under `/api/v1/admin/` needs a session (and the CSRF token on unsafe methods, no exemption) from the spec, and a chi middleware after the request validator answers 403 `urn:maiak:problem:forbidden` unless the session's user has the flag. It works on the path prefix, so an admin operation added later cannot forget it; a contract test fixes the list of admin operations and an integration test calls each one as a registered user (403) and without a session (401).
- **Cross-tenant access only through definer functions.** `admin_stats`, `admin_list_tenants`, `admin_get_tenant`, `admin_set_tenant_plan`, `admin_set_tenant_status`, `admin_delete_tenant`, `admin_list_users` and `admin_reset_user_password` are `SECURITY DEFINER`, owned by `maiak_owner`, pin `search_path = public, pg_temp`, are executable by `maiak_api` only and are in the schema-lint `definerAllowList`; tests show that `maiak_worker` and an unrelated role are refused. They read tenant tables through the existing `owner_*` read policies (`owner_membership_lookup`, `owner_claim_read`) and need no new policy. No Go code issues cross-tenant SQL, and no role has `BYPASSRLS`.
- **The actor argument and its trust model.** Each `admin_*` function takes the acting user's id as its first argument and checks inside, before anything else, that the user exists, is `active` and has the flag (SQLSTATE `MKA01`, 403). The api is trusted for the identity of the session, exactly as it is trusted to set `app.tenant_id` for RLS: a compromised api process could pass the platform admin's id. The check inside still matters: the api's own guard and the function check are independent, a bug that skips the middleware or calls a function with the wrong id for a normal user fails closed, and the only ids that pass are those of the flagged user, whose flag only the bootstrap controls. Internal invoker helpers (`admin_require_platform_admin`, `admin_audit`) are executable by nobody but the owner.
- **Audit in the same transaction.** Every mutating function writes its own `audit_log` row into the **target** tenant (under that tenant's `app.tenant_id`, restored afterwards), with the actor, the entity, the client IP and metadata: `admin.tenant.plan_changed` (`from`, `to`), `admin.tenant.suspended` / `admin.tenant.unsuspended` (`from`, `to`), `admin.tenant.deleted` (`status`, `plan` before), `admin.user.password_reset` (`sessions_revoked`). Never a password or a hash. A call that changes nothing (same plan, same status, already deleted) writes no row. `maiak_admin_actions_total{action}` counts the changes.
- **Guard rails, inside the functions.** The `default` tenant can never be suspended or deleted (`MKA05`); an admin cannot suspend or delete a tenant it belongs to (`MKA06`); both answer 409 `urn:maiak:problem:protected-tenant`. A deleted tenant cannot be changed (409 `tenant-deleted`); deleting it again is a no-op (204). A platform admin's password cannot be reset through the panel (`MKA07`, 409 `system-admin`): its credentials come from the `maiak-admin` Secret. Unknown plans and statuses are 422 with `fieldErrors`.
- **Password reset.** The api generates a 24-character temporary password (120 random bits, an alphabet without look-alike characters; it satisfies the registration policy), hashes it with the existing argon2id function and parameters through the bounded hash queue of login and registration (429 when full), and passes only the hash. The function stores it and deletes all of the user's sessions in every tenant (`auth_revoke_user_sessions`). The password is in the answer only (`Cache-Control: no-store` like every API answer), never logged and never audited; the admin hands it over by hand (L-232). The user cannot change it afterwards (L-233).
- **Suspension and soft delete.** Suspend sets `tenants.status = 'suspended'`; soft delete sets `deleted_at` and also `status = 'suspended'`, so a previous release that only checks the status refuses the login too. Effects, all enforced by existing code unless noted: sessions are refused by `auth_lookup_session`; `claim_due_monitors` claims no monitor; `heartbeat_ping` answers 204 without recording; `list_due_heartbeats` skips the tenant's heartbeats; new in this ADR, `claim_deliveries` claims no Slack delivery of an inactive tenant (pending ones wait and are sent after an unsuspend). Data is never deleted (L-234).
- **Login of a suspended tenant.** A correct password for a user whose tenant is suspended or deleted answers 403 `urn:maiak:problem:account-suspended`; a wrong password still gets the generic 401, so the state is never revealed to a guess. The attempt counts against the limiters like a failure and is audited (`auth.login.failed`, reason `tenant_suspended`); `maiak_auth_logins_total` has the new result `suspended`. `auth_login_tenant` (same signature, new body) returns a deleted tenant when the user has no live one, so this answer also covers deletion; a live membership still wins.
- **Plans and existing usage.** A plan change keeps every monitor, heartbeat and channel. Quotas are checked only when a resource is created (ADR-0093), so usage above the new limit blocks new creations (409 `plan-limit-reached`) and nothing else; `GET /usage` shows the usage above the limit. `admin_set_tenant_plan` locks the tenant row like `plans.CheckCreate`, so a plan change and a concurrent create of the same tenant are serialised.
- **No impersonation and no admin-grant API**, as ADR-0092 decided: the panel shows and changes tenants and users, it never acts inside a tenant as one of its users.
- **Web.** An `/admin` area routed only when `isPlatformAdmin` (others see the not-found page), linked from the top bar for the admin only. The temporary password lives in component state only and is gone on navigation.

## Consequences
- One flag, one admin. A second platform admin, or an admin who is not the system admin, needs a decision and a way to grant the flag that is not an API (ledger when needed).
- Nine more definer functions in the allow-list, each with the actor check; a new admin function must follow the same shape (actor first, `admin_require_platform_admin`, audit through `admin_audit`).
- Expand/contract: the migration adds a defaulted column, narrows `INSERT` on `users` to the columns both releases write, adds functions the previous release does not call and replaces two bodies with unchanged signatures. During the rollout an old api pod answers a login of a user whose only tenant was just deleted with 500 instead of 401 (it cannot read a deleted tenant); the admin panel exists only in the new release, so this needs a deletion during the rollout.
- Ledger: L-230 (no audit-log viewer), L-231 (no rate limit on admin actions), L-232 (manual delivery of temporary passwords), L-233 (no forced password change), L-234 (no hard delete or restore of tenants), L-235 (heartbeats alert right after an unsuspend), R-190 (the api is trusted with the actor id); L-192 updated.

## Alternatives considered
- **A `BYPASSRLS` role or a second pool for the admin.** Rejected in ADR-0092: one mistake in a query would expose every tenant, and RLS would no longer be the backstop.
- **Owner policies with `USING (true)` for each table the panel reads.** Policies apply to every function the owner runs; definer functions with explicit filters keep the exposure in a few reviewed bodies, and the reads needed here are covered by the existing read policies.
- **Checking the flag only in the api.** The definer functions would then be a cross-tenant API for anything that can execute them as `maiak_api`, guarded by Go code alone; the in-function check costs one indexed lookup.
- **Passing the session token instead of the user id to the functions.** The function could resolve the session itself, but the api is trusted with the session already (it resolves it for every request), and token handling in SQL would add a second place that hashes and validates tokens.
- **Deleting a tenant's sessions on suspension.** `auth_lookup_session` already refuses them, and an unsuspend then restores access without a new login; deletion of data, sessions included, belongs to a later hard-delete decision (L-234).
