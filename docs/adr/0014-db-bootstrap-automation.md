# ADR-0014: Automatic database bootstrap as a hook Job

- Status: Accepted
- Date: 2026-10-20

## Context
Migrations need an existing database and roles, which only an administrator can create. A manual script (first design) does not reproduce across environments. Facts for the first deployment: the target is the existing RDS instance `grafana`; its master user is `grafana` (Grafana's own login, not RDS-managed), and on PostgreSQL 15 even `CREATEROLE` can alter other roles, so no least-privilege provisioner exists on this instance.

## Decision
- `maiakctl db bootstrap` creates, idempotently, the database `maiak`, the roles `maiak_owner`, `maiak_api`, `maiak_worker` (no superuser, no `BYPASSRLS`, connection limits, timeouts) and the `citext` extension.
- It runs as an ArgoCD hook Job `maiak-db-bootstrap` (wave -3) before the migration Job, enabled by `dbBootstrap.enabled`. It never runs inside `api`, `worker` or `jobs`, so the long-running pods never hold the admin login.
- The admin login comes from an ExternalSecret hook (wave -4) on `platform/grafana/db` (no copy), deleted by ArgoCD after the Job succeeds (`HookSucceeded`).
- The Job generates the role passwords on first run and creates the Kubernetes Secret `maiak-db` first (so a password is never lost), then applies them. The Secret holds `api_url`, `worker_url`, `owner_url` and the three passwords. It is not managed by ArgoCD. A missing Secret is simply regenerated by the next run (`ALTER ROLE`). The Job's ServiceAccount is the only one with a token, with a Role limited to creating secrets and to get/update/patch on `maiak-db`.
- Encryption keys stay in AWS Secrets Manager (`platform/maiak/crypto`): losing a key means losing encrypted data, so they must not live only in the cluster. The admin hash comes from `platform/maiak/admin`.
- The flag is enabled for the first deployment and then switched off by a commit (`dbBootstrap.enabled=false`). It is switched on again for a new database, a new environment or a dedicated RDS (L-009).

## Consequences
- While enabled, whoever can change this chart or its image can use the RDS login, which is Grafana's. The image is built from a repository under a personal GitHub account. Tracked as risk R-009.
- A new environment needs only a reachable instance and its admin secret.
- The same code runs in CI against a scratch Postgres, so the bootstrap is tested.

## Alternatives considered
- Manual runbook only: not reproducible, depends on a person.
- Init container in every pod: every replica, including the worker, would hold the admin login.
- A copy of the master login in `platform/maiak/db-admin`: drifts when the password rotates.
- Passwords in Secrets Manager: needs AWS access from the Job; unnecessary because the Job can always regenerate them.

## Implementation notes (2026-10-20)
- Role passwords are sent to PostgreSQL as SCRAM verifiers, never as plaintext statements; statements are built server-side with `format(%I, %L)`.
- A Secret with missing password keys makes the run fail instead of overwriting; a Secret with missing or stale `*_url` keys gets its URLs rebuilt.
- Tested only with a superuser admin and a `CREATEROLE CREATEDB` approximation of `rds_superuser`; the real RDS path is verified at the first deploy (L-022).

## Amendment (2026-10-20, ADR-0091)
The encryption keys and the admin hash no longer have to come from AWS Secrets Manager: by default a separate hook Job without database credentials generates them in the cluster. Losing a generated key only costs the Slack webhook URL, which is re-entered. Secrets Manager stays available per Secret (`secrets.*.source: externalSecret`).
