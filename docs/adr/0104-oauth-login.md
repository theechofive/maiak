# ADR-0104: OAuth login (Google Workspace, GitHub)

Status: accepted (2026-11-06)

## Context
Colleagues will use one shared installation. Password-only login does not fit a company: no shared identity, no way to join by company domain. `auth_identities` exists since the first migration and is unused (L-007, L-269). The product has no real users yet, so the schema and flows can change freely.

## Decision
- **Providers:** Google (OpenID Connect, Workspace aware) and GitHub (OAuth 2.0). GitLab and generic OIDC are later (L-301). The code has one `Provider` interface (declared in `internal/oauth`, the consumer side) with two implementations; no provider tokens are stored, only the identity (`provider`, `subject`, verified email).
- **Flow:** authorization code with PKCE (S256), `state` and `nonce` in one short-lived (10 min) HMAC-signed `HttpOnly` cookie bound to the browser, exact redirect URI from `MAIAK_PUBLIC_URL`. `POST /api/v1/auth/oauth/{provider}/start` (body: optional `inviteToken`, `intent` login or link) returns the provider URL; `GET /api/v1/auth/oauth/{provider}/callback` finishes the flow, sets the normal session cookie and redirects to `/` (errors redirect to `/login?error=<code>`, never reflecting provider text). The invitation token travels in the POST body, never in a URL.
- **Identity rules:**
  - Google: `email_verified` must be true; the stable key is `sub`. GitHub: the stable key is the numeric user id; only the primary verified address from `/user/emails` is used.
  - A login finds the user by `(provider, subject)`. No match: a new user is created only when (a) an invitation token is presented and valid, or (b) the verified Google `hd` claim equals a domain claimed by an organization with auto-join (below), or (c) self-registration is enabled (`MAIAK_REGISTRATION_ENABLED`). Otherwise the answer is `not_invited`.
  - **No automatic linking to an existing account by email.** Passwords registered with an unverified email (R-120) would allow pre-hijacking: an attacker registers `victim@company` with a password, the victim signs in with Google and lands in the attacker's account. An existing user links a provider only while logged in (`intent: link`, profile page); an OAuth email that belongs to an existing unlinked account answers `account_exists` (sign in with the password, then link). OAuth-created users have `email_verified_at` set.
  - Unlinking is allowed only when another way to sign in remains (password or another identity).
- **Domain auto-join (Google Workspace):** an organization owner claims a domain (`org_auth_domains`: `tenant_id`, `domain`, `default_role` admin/member/viewer with `viewer` default, `enabled`). Joining requires the `hd` claim to match and `email_verified`; a domain can be claimed by one organization only (global unique), and claiming needs the owner to be signed in with a Google account whose `hd` equals the domain (proof of control). Joining adds the user to that organization (and to its Default project through `all_members`). Gmail addresses (no `hd`) never auto-join.
- **Policy switch:** `MAIAK_PASSWORD_LOGIN_ENABLED` (default true) turns off the password form for everyone except the platform admin login (`/login?admin`), so a company can run OAuth-only without losing the break-glass account.
- **Configuration:** `MAIAK_PUBLIC_URL`, `MAIAK_OAUTH_GOOGLE_CLIENT_ID/_SECRET`, `MAIAK_OAUTH_GITHUB_CLIENT_ID/_SECRET`; a provider with no credentials is hidden (`GET /api/v1/auth/providers`, public, lists enabled providers and the password switch). Secrets come from the ExternalSecret `platform/maiak/...`, never from values files.
- **Sessions and rate limits:** the same session creation as password login (a user with several organizations enters the last used or the oldest membership, switcher as before); callbacks share the login rate limiter by IP; every outcome writes an audit row (`auth.oauth_login`, `auth.oauth_failed`, `auth.identity_linked`, `auth.identity_unlinked`, `org.auth_domain_changed`).
- **Authorization:** the new operations are added to `internal/authz` (start and callback public; link and unlink any signed-in user; auth domains owner only), the all-operations test keeps denying unknown ones.

## Consequences
- A shared installation works with company Google accounts and no invitation per person; GitHub works through invitations or linking.
- Members who only have an OAuth identity cannot use the password form; recovery is the identity provider's.
- Not built: SAML, SCIM, group-to-role mapping, GitHub organization membership checks, GitLab (L-301..L-303).

## Implementation notes (O-01, 2026-11-06)
- **Schema** (`20261106180000_oauth_login.sql`, expand only): `users.email_verified_at` (insert and update grant for the api), `auth_identities.email`, `hosted_domain`, `last_login_at` (column UPDATE grant; subject and owner stay immutable), provider limited to `google`/`github`, one identity per provider and user; `org_auth_domains` with forced RLS, global unique `domain`, `default_role` viewer by default; definer `auth_domain_lookup(domain)` (api only, allow-listed in the schema lint).
- **`internal/oauth`:** `Provider` interface, `Flow` (PKCE S256, 32-byte random state, nonce and verifier, HMAC-SHA256 signed cookie `maiak_oauth`, `Path=/api/v1/auth/oauth/`, `HttpOnly`, `SameSite=Lax`, 10 minutes; it carries the user id of a link and the SHA-256 of an invitation token, never the token). Google: discovery from the issuer (checked), RS256 ID token against the published keys with `iss`, `aud`, `azp`, `exp`, `iat` and `nonce`; `email_verified` required. GitHub: numeric id, primary verified address from `/user/emails`; the access token is used for the two calls and dropped. Provider clients: 15 s overall timeout, no proxy from the environment, redirects only to the same scheme and host, answers capped at 1 MiB, error bodies never returned.
- **State key:** derived with HKDF from the active encryption key instead of a new secret (L-304).
- **Proof of control for a domain:** the `hd` of the owner's linked Google identity, stored at each Google sign-in or link (`hosted_domain`, an addition to the schema above; L-306). Auto-join applies to new accounts only (L-305).
- **Order of the rules for an unknown identity:** an existing account with the email answers `account_exists` first (also with an invitation); then invitation, then claimed domain (Google with `hd` only), then open registration (a new organization on the free plan, like password registration), else `not_invited`. A linked user with an invitation joins that organization.
- **Redirects:** the callback answers 303. Sign-in success goes to `/`, errors to `/login?error=<code>`; link success to `/profile?linked=<provider>` and link errors to `/profile?error=<code>` (O-02 builds that page). Codes are listed in the spec of `oauthCallback`. Every callback counts against the login's per-IP limiter until it succeeds (also a forged one), and each failure writes `auth.oauth_failed` with a short reason, never provider text.
- **Password switch:** with `MAIAK_PASSWORD_LOGIN_ENABLED=false`, password login answers 403 `password-login-disabled` before any lookup for every login but the configured admin login, and registration with a password (with or without an invitation) is refused the same way. A password that cannot be used does not count for the unlink rule (it does for the admin).
- **Configuration:** `MAIAK_OAUTH_{GOOGLE,GITHUB}_CLIENT_{ID,SECRET}` in pairs; password login off needs a provider (startup fails otherwise). Chart: `oauth.google.enabled`, `oauth.github.enabled`, `config.passwordLoginEnabled`, Secret `maiak-oauth` from the ExternalSecret `secrets.oauth.remoteKey` (`platform/maiak/oauth`).
- **Metrics:** `maiak_auth_oauth_logins_total{provider,result}`.

## Review fixes (O-04, 2026-11-06)
- **Domain claims are limited by the operator** (M1): `MAIAK_OAUTH_ALLOWED_DOMAINS` (Helm `oauth.allowedDomains`) lists the lowercase Workspace domains organizations may claim; empty (the default) turns claiming and domain auto-join off, and a stored claim stops joining as soon as its domain leaves the list (`domain-not-allowed`, 403). The proof of control must be fresh: the owner's Google identity signed in or was linked with that `hd` within 10 minutes (the web sends the owner through the link flow right before claiming). A claim always starts with `defaultRole` viewer; owners raise it afterwards with PATCH. Rationale: any member of a Workspace has a matching `hd`, so without these limits an employee could squat the company domain (R-214, L-309).
- **State cookie** (M2): `__Host-maiak_oauth` with `Secure`, `Path=/`, no `Domain`, `HttpOnly`, `SameSite=Lax` whenever `MAIAK_COOKIE_SECURE` is true, so neither a sibling subdomain nor a plain-HTTP response can plant or replace it. Only with insecure cookies (local development) the unprefixed `maiak_oauth` scoped to `/api/v1/auth/oauth/` is used.
- **Provider fetches** (L1): Google discovery and key fetches run outside the provider's mutex and are deduplicated (singleflight); a failed discovery refresh serves the stale copy and is not retried for 30 s (L-308).
- **Concurrent links** (L2): a unique violation on `auth_identities_user_provider_key` answers `already_linked` and is audited like the other link failures.
