# ADR-0095: Review fixes P-07: admin adoption, tenant creation through the database, random slugs

- Status: Accepted
- Date: 2026-10-21

## Context
The security review of plans (P-01) and registration (P-02) found:
- **M1 (R-160).** With open registration, a stranger can register `ops@company.com`. If the operator later sets `MAIAK_ADMIN_LOGIN=ops@company.com`, `BootstrapAdmin` adopted the stranger's user as owner of `default`, disabled the old admin and deleted only the adopted user's `default` sessions. `auth_login_tenant` returned the oldest membership, so the operator's login landed in the stranger's tenant, and the stranger's own sessions stayed valid.
- **m1.** `maiak_api` had table-wide `INSERT` and `UPDATE` on `tenants`: a compromised api could move any tenant to the `internal` plan, rewrite `limits`, `status` or `deleted_at`, and it chose the plan of a new tenant itself.
- **m2.** Nothing forced `tenants.limits` to be a JSON object, although `internal/plans` reads it key by key.
- **m3.** Registered tenant slugs embedded the email's local part (`john-smith-k3x9qa`), which leaks a personal identifier into URLs and logs.

## Decision
- **No adoption of a user of another tenant.** When the configured login already exists, `BootstrapAdmin` counts the user's memberships outside `default` (deleted tenants included) with `auth_count_other_memberships(user_id, tenant_id)`. If there is any, it fails with `ErrAdminLoginInUse`, writes nothing and the api does not start; the operator chooses another login or removes that user's other memberships deliberately. This also holds for an already adopted admin: the admin of `default` must not be a member of another tenant (a platform-admin role is a flag, not a membership, ADR-0092), and a crash loop is preferable to an admin who can be steered into a stranger's tenant.
- **Adoption revokes every session.** An existing user that is not yet the active owner of `default` (adoption, or rotating back to a disabled previous admin), a changed password hash and every retired previous owner have all their sessions deleted in every tenant by `auth_revoke_user_sessions(user_id)`. The function finds the sessions through the existing `owner_session_lookup` policy and deletes them tenant by tenant under the normal isolation policy (it sets `app.tenant_id` per tenant and restores the caller's value), so no broader `DELETE` policy is needed. A function `SET app.tenant_id` clause would restore the value automatically, but a custom setting in a function `SET` clause needs superuser on Postgres 15+.
- **The default tenant wins the login.** `auth_login_tenant` (same signature, new body, `CREATE OR REPLACE`) returns the `default` tenant when the user is a member of it, otherwise the oldest membership as before (L-190).
- **Tenants are created by the database.** `auth_create_tenant(id, slug, name)` inserts a tenant on `internal` only when the slug is `default` and on `free` otherwise, returns the id, or NULL when the slug is taken (no aborted transaction). Registration (`tenants.Create`) and `BootstrapAdmin` (`tenants.Ensure`) use it. The id stays a UUIDv7 generated by the app, hence the extra argument. `maiak_api` keeps only `UPDATE (updated_at)` on `tenants`, which is what `SELECT ... FOR UPDATE` in `tenants.LockQuota` needs. `INSERT` is revoked one release later (L-210): the previous release inserts tenants directly during a rolling update.
- **`CHECK (jsonb_typeof(limits) = 'object')`** on `tenants.limits` (`tenants_limits_is_object`).
- **Random slugs.** A registered tenant's slug is `t-` and 10 lowercase base32 characters (50 random bits), retried on a collision; it never contains any part of the email and can never be `default`. The tenant name is still the email's domain.
- All three new functions are `SECURITY DEFINER`, owned by `maiak_owner`, pin `search_path = public, pg_temp`, are executable by `maiak_api` only and are in the schema-lint `definerAllowList`; tests check that `maiak_worker` and an unrelated role are refused.
- Tests added for the remaining review items: registration refuses `text/plain`, form-encoded and multipart bodies exactly like the login (no cross-site form can plant a tenant in a victim's browser), and the tenant isolation test covers incidents, stats, checks, pause, resume, patch, delete, heartbeat token regeneration, Slack settings and test, usage, and that the other tenant's monitors (including `paused`) are unchanged.

## Consequences
- R-160 is closed. Setting `MAIAK_ADMIN_LOGIN` to an email that a stranger registered fails the rollout visibly (the new pods do not become ready) instead of handing over the default tenant.
- Plan and status changes of tenants are left to migrations, the owner role and the future platform-admin definer functions (P-04).
- Expand/contract: the migration only adds grants-narrowing that the previous release does not need (`UPDATE` on `tenants` was used by nothing but the row lock) and functions it does not call; L-210 tracks the contract step.
- Ledger: R-160 done, L-190 updated, L-210 added.

## Alternatives considered
- A `FOR DELETE TO maiak_owner USING (true)` policy on `sessions` for the revocation: simpler, but it would make the narrower `owner_session_purge` (expired sessions only) meaningless.
- Adopting the user and removing its other memberships: destroys a stranger's data on a configuration change and still trusts the stranger's account.
- Passing the plan to `auth_create_tenant`: the api role could then still choose `internal`.
