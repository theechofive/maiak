# ADR-0094: Heartbeat (watchdog) monitors

- Status: Accepted
- Date: 2026-10-21

## Context
ADR-0092 decided a monitor type for dead man's switches (task P-03): clients run Prometheus Alertmanager, whose always-firing `Watchdog` alert is sent to a webhook receiver every repeat interval. When the pings stop, the client's alerting pipeline is broken and someone must be told. This is the first request path without a session, so it must be cheap, constant in its answers and rate limited, and the secret must never be stored or logged in clear.

The incident machine, the outbox and the Slack formats already exist for HTTPS monitors (ADR-0007, ADR-0016, ADR-0019). Since B-19 (ADR-0040) `maiak_api` cannot write the scheduler state, the check-time columns of `monitor_state` or the outbox, and `TestIntegrationAPIRuntimeGrants` enforces it.

## Decision
- **Model.** A monitor of `type` `heartbeat` in the same `monitors` table. The MVP constraints (60 s interval, 10 s timeout) now bind `http` only; `monitors_heartbeat_check` requires an expected interval of 60-86400 s in `interval_seconds`, an integer `config.graceSeconds` of 0-3600 and `failure_threshold` 1 (one missed deadline is down). Defaults: 300 s and 60 s. The create transaction also inserts the home `monitor_locations` row, a `monitor_location_state` row parked at `next_run_at = infinity` (it only carries the incident machine's per-location state) and the `monitor_state` row, like an http monitor, so the existing machine, pause, resume and delete hooks are reused unchanged.
- **Token.** 32 random bytes, URL-safe base64 without padding. Only the SHA-256 is stored, in `heartbeat_tokens` (one row per heartbeat, RLS forced, composite FK, `token_hash` unique). The URL `MAIAK_PUBLIC_URL/api/v1/heartbeat/<token>` is returned only by the create response (`heartbeatUrl`) and by `POST /api/v1/monitors/{id}/heartbeat-token` (session and CSRF), which replaces the hash: the old URL then answers like any unknown token. The server cannot show a URL again.
- **Public ping.** `GET` and `POST /api/v1/heartbeat/{token}` need no session and no CSRF token (the contract tests list them as deliberately public; the POST is CSRF-exempt because there is no session to carry a token, and the token in the URL is the credential). The body is ignored (at most 64 KiB read). The api hashes whatever token it gets and calls the `SECURITY DEFINER` function `heartbeat_ping(hash)` (owned by `maiak_owner`, `search_path` pinned, `EXECUTE` for `maiak_api` only, allow-listed in the schema lint, reading and writing through the `owner_heartbeat_read` / `owner_heartbeat_ping` policies). It records `last_ping_at` for a live heartbeat and returns the tenant, the monitor and whether it recorded; a paused or deleted heartbeat, or one of an inactive tenant, answers `204` but records nothing. Any unknown token gets the same `404` problem, whose `instance` is the route template, never the path. Limits in memory per api replica: one accepted ping per token per second, 30 unknown-token pings per client IP per 5 minutes; both answer `429` with `Retry-After`. `maiak_heartbeat_pings_total{result}` counts the outcomes.
- **Evaluation in jobs, not in the ping.** The ping only records the time. A singleton jobs task `evaluate_heartbeats` (every 30 s, advisory lock like the other housekeeping tasks) calls the read-only definer function `list_due_heartbeats(n)` (`EXECUTE` for `maiak_worker` only) for live heartbeats with a ping the machine has not seen or a passed deadline not applied yet, and handles each in its own tenant transaction that first locks the `heartbeat_tokens` row and re-reads it with the database clock: an unseen ping becomes an OK result at the ping time (`applied_ping_at`), a passed deadline a failed result with error kind `heartbeat_missed` at the deadline (`missed_deadline`), both through `incidents.Service.ApplyResult`. So an incident opens at the deadline, once per deadline, with an outbox row when `notify_slack` is on and the tenant has an active Slack channel, and the next ping resolves it with the usual resolved message. `maiak_jobs_heartbeats_missed_total` counts applied misses.
- **Deadline.** The newer of `waiting_since` (creation, or the last resume) and `last_ping_at`, plus the interval and the grace; a heartbeat is overdue only strictly after it. A never-pinged heartbeat stays `unknown` until its first ping (`up`) or its first deadline (`down`). Resume sets `waiting_since = now()` and marks older pings as applied. Pause, resume and delete take the `heartbeat_tokens` row lock before the state rows, like the evaluation, so they are serialised; pause and delete resolve an open incident without a notification as for http monitors.
- **Workers never see heartbeats.** `claim_due_monitors` keeps its signature (workers of the previous release keep working) and gets a body that claims `type = 'http'` only; `reset_monitor_runtime` keeps a heartbeat's row at `infinity`. Heartbeats have no `check_results`, so no uptime, latency or checks.
- **Quota.** `plans.CheckCreate` counts live http monitors for `monitors` and live heartbeats for `heartbeats` (closes L-181), under the tenant row lock as before; `/usage` reports both.
- **Contract.** `POST /monitors` takes an optional `type` (`http` default) and the optional fields `expectedIntervalSeconds` and `graceSeconds` (no schema defaults, so http requests stay free of them); `url` is no longer required by the schema, the server requires it for `http` (422). A heartbeat ignores `intervalSeconds`, `timeoutSeconds` (their schema defaults fill every request) and `failureThreshold`, and refuses `url` and `expectedStatus` (422); an http monitor refuses the heartbeat fields. List and detail carry `type` and the nullable `lastPingAt`, `expectedIntervalSeconds`, `graceSeconds`. `oasdiff breaking` reports no breaking change. Slack's opened message explains `heartbeat_missed`.

## Consequences
- Detection and recovery lag the event by up to 30 s (the task interval); the incident still starts at the deadline and resolves at the ping time.
- The public path is one hash and one function call; nothing tenant-scoped runs before the token is known.
- No new grants on the scheduler, state or outbox tables for `maiak_api`; ADR-0040 stands.
- Two more definer functions and two `owner_*` policies in the schema-lint allow-lists, with role tests.
- Ledger: per-replica ping limits (L-200), no ping history (L-201), evaluation lag and full scan (L-202), the token in URLs and gateway logs (R-161).

## Alternatives considered
- Applying the OK result in the api right after the ping (one tenant transaction per ping): needs `maiak_api` to update `monitor_location_state`, `monitor_state.last_checked_at` and insert outbox rows, reversing ADR-0040, and puts a tenant transaction on the unauthenticated path. The 30 s recovery lag was judged acceptable for a watchdog.
- A `claim_overdue_heartbeats` that marks rows when it returns them: a crash between the claim and the tenant transaction would lose the miss; the read-only list plus marking in the tenant transaction is crash-safe, and the advisory lock already makes the task a singleton.
- Recording every ping in `check_results`: uptime for heartbeats, but a write per ping into the partitioned table and rollups that mean nothing for a watchdog (L-201).
- Storing the token (or an HMAC with a server key) to show it again: a database or backup leak would yield working URLs; regenerating is cheap.
- A separate `heartbeats` table instead of a monitor type: the incident machine, quotas, pause, delete and the dashboard would need a second path.
