# ADR-0100: Notification channels: several Slack channels, per-monitor selection, reminders

- Status: Accepted
- Date: 2026-10-27

## Context
ADR-0019 allowed one Slack channel per tenant (a partial unique index) and left `monitor_channels` unused; ADR-0050 exposed it as `GET/PUT /settings/slack` and `POST /settings/slack/test`. ADR-0099 (Phase 3, task S-01) asks for several channels per tenant within the plan quota, each with its own events, an optional mention and optional reminders for incidents that stay open, chosen per monitor, and for a way to delete a channel (L-081). Removing `/settings/slack` is a breaking API change, so it needs this ADR.

## Decision
- **API.** `/api/v1/settings/slack` and `/settings/slack/test` are removed and replaced by `/api/v1/channels` (list, create) and `/api/v1/channels/{channelId}` (get, patch, delete) plus `POST /api/v1/channels/{channelId}/test`. The problem type `slack-not-configured` is gone: an unknown channel is 404. The SPA is the only client and changes in the same commit. Spec version 0.5.0.
- **Channel fields.** `name` (1-60, trimmed, no control or invisible formatting characters), `type` (`slack_webhook` only), write-only `webhookUrl` (the ADR-0016 rule, AES-256-GCM with the AAD bound to the channel id, never returned or logged), `events` (non-empty subset of `down`, `recovered`, `tls_expiring`, default all), `mention` (at most three of `@here`, `@channel`, `<!subteam^ID>`, `<@UID>`, matched by a strict pattern in the service, in a database `CHECK` and again before sending; rendered as `<!here>`/`<!channel>`/as written, and put only in front of `opened` and `reminder` messages), `reminderMinutes` (0 = off, or 5-1440), `status` (`active`/`failed`). A patch with a new webhook makes a failed channel active again and keeps its id. Audit actions `channel.created`, `channel.updated` (field names only), `channel.deleted` (counts), `channel.tested` (result kind).
- **Quota.** Creating a channel calls `plans.CheckCreate(..., ResourceChannel)` under the tenant row lock; deleted channels do not count (`CountChannels` filters `deleted_at`).
- **Routing.** `monitors.channelIds` (at most 10, live channels of the tenant, written to `monitor_channels` through `notify.SetMonitorChannels`, which takes `FOR SHARE` locks so a concurrent delete cannot leave a link behind). `notifySlack` stays the on/off switch; with no selection a monitor notifies every active channel of the tenant. The incident service writes one outbox row per emitted kind and per eligible channel whose events contain the kind's event (`opened` -> `down`, `resolved` -> `recovered`, `tls_expiring` -> `tls_expiring`), in the result transaction as before (ADR-0007).
- **Delivery order.** `claim_deliveries` (new body, same signature) serialises deliveries per (monitor, channel) instead of per monitor, so one channel waiting for a retry does not hold back the others.
- **Reminders.** A jobs housekeeping task `enqueue_incident_reminders` runs every minute under its advisory lock and calls the definer function `enqueue_incident_reminders(limit)` (owner `maiak_owner`, `search_path = public, pg_temp`, `EXECUTE` for `maiak_worker` only, owner-only read policies on `incidents`, `notification_channels`, `monitor_channels` and an insert policy on `notification_deliveries`). For every open incident and every channel that would receive its `down` event (active, not deleted, `reminderMinutes > 0`, selected or no selection, monitor notifies and is not paused or deleted, tenant active) it inserts a `reminder` delivery once `reminderMinutes` have passed since the newest `opened` or `reminder` delivery of that incident to that channel, or since the incident started. Ids are UUIDv7 built in SQL from the clock; the payload holds the monitor name and the duration at enqueue time. Message: `:bell: *{name}* is still down ({duration})`. A non-concurrent index `(incident_id, channel_id, created_at)` is added in a separate `NO TRANSACTION` migration.
- **Delete.** `DELETE /channels/{id}` soft-deletes the row (`deleted_at`, the encrypted webhook wiped, `status` set to `failed`), removes its `monitor_channels` rows and fails its pending deliveries with `last_error = 'channel_deleted'` through the definer function `fail_deleted_channel_deliveries(channel_id)` (`maiak_api` only; only for a deleted channel of the caller's `app.tenant_id`), all in one tenant transaction. Deliveries already in progress fail in jobs (`channel_deleted`). The row stays because `notification_deliveries` references it.
- **Migration.** `20261027210000_notification_channels.sql` adds the columns with constant defaults (existing channels become "Slack" with every event, no mention, no reminders), makes `config_encrypted` nullable with a check that live channels keep it, drops `notification_channels_one_slack_idx`, allows the `reminder` kind, replaces `claim_deliveries` and creates the two functions and four policies. It is forward-only and expand/contract with these caveats during the rollout (L-260): the previous api creates a first channel with `ON CONFLICT` on the dropped index and gets an error (500) until it is replaced; the previous jobs cannot format a `reminder` and marks it failed (`bad_payload`). A deleted channel is `failed`, so the previous worker (first active Slack channel of the tenant) and jobs never use it.

## Consequences
- ADR-0019 is superseded; the parts of ADR-0050 about the `/settings/slack` endpoints are superseded (the storage, AAD, sender and failure semantics stay). L-081 is closed.
- A monitor whose only selected channel is deleted falls back to every active channel (empty selection); the delete confirmation says so (L-261).
- Reminders repeat until the incident resolves or the channel's reminder is turned off; there is no acknowledge or snooze (L-262).
- The test-message limit stays one per 5 s per tenant and per api replica (R-100), now shared by all channels of the tenant.
- `oasdiff` reports the removed operations and schemas as breaking; this ADR accepts it.

## Alternatives considered
- Keeping `/settings/slack` as an alias of the first channel: two APIs for the same rows, and no client needs it.
- Hard delete of channels with `ON DELETE CASCADE` or `SET NULL` from `notification_deliveries`: loses the delivery history or needs a nullable `channel_id` everywhere.
- Queuing reminders from Go in tenant transactions: needs a cross-tenant scan anyway; one definer function keeps it in one statement under the existing housekeeping lock.
- Selecting channels by writing `monitor_channels` from `notifySlack` (all channels) on every channel create: rows to maintain for the common case and a migration of existing monitors; the empty selection means "all" instead.
